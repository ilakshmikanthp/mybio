## Why product companies interview differently

Services interviews ask what you used. Product interviews ask **what you owned, what you decided, why, and what happened to the user or the business afterwards**. Every answer this week should therefore carry four things: the decision, the alternatives you rejected, the trade-off you accepted, and a number. If you do not have a number yet, finding one is the work (see the metrics worksheet).

## Day 1: Pitch and narrative

### 60-second pitch (draft, edit to your voice)

> I'm a lead full stack engineer with 17+ years in software, the last 10+ in cloud web. I started in embedded and industrial systems: Modbus, embedded Linux, monitoring for the Dubai Metro and ISRO GPS stations. That taught me to build things that cannot go down. Since moving fully into web I have built React and Next.js products for EA, Walmart and GAP, and Advance Auto Parts: micro-frontends, design systems, serverless authentication, and a JSP-to-Next.js migration. At EA I work on the FanCare Help Center and passwordless sign-in, and I'm driving an agentic, spec-driven workflow that connects Figma and Jira through MCP. I'm now looking for a product company where I can own a surface end to end and see its impact on users.

Rules: end on what you want next, not on a list of tools. Practise until it takes 55 to 65 seconds.

### Questions to answer in writing

- Why did you move from embedded and industrial systems to web? (What did embedded teach you that web engineers often lack?)
- Why a product company now, after consulting and client work?
- What is the one thing you are proudest of in the last 3 years, and why?
- What do you want to own in the next role?

## Day 2: STAR story bank

Template for every story. Keep each under 2 minutes spoken.

```
Situation   One or two sentences of context. Who, what, why it mattered.
Task        What was specifically yours (not the team's).
Action      3 to 4 concrete things YOU did. Include the decision and the rejected alternative.
Result      A number (time, %, errors, adoption) and what you learned.
```

## Day 5: JavaScript and TypeScript fundamentals

Explain each out loud in 60 seconds. Short model answers are given so you can check yourself.

<Check id="w1-js-1">Event loop and ordering</Check>

Synchronous code runs on the call stack. When it empties, the engine drains the **microtask queue** (promise callbacks, `queueMicrotask`) completely, then takes one **macrotask** (`setTimeout`, I/O, UI events), then drains microtasks again. So a resolved promise callback always runs before a `setTimeout(fn, 0)` callback.

<Check id="w1-js-2">Closures, scope, hoisting, the temporal dead zone</Check>

A closure is a function plus the variables of the scope it was created in. `var` is function-scoped and hoisted with the value `undefined`. `let` and `const` are block-scoped and hoisted but unusable until their declaration runs (the temporal dead zone).

<Check id="w1-js-3">`this` binding</Check>

Decided at call time: `new` first, then explicit `call` / `apply` / `bind`, then method call (the object before the dot), else default (undefined in strict mode). Arrow functions have no own `this` and capture the enclosing one.

<Check id="w1-js-4">Prototypes and classes</Check>

Objects delegate property lookups along the prototype chain. `class` is syntax over constructor functions and prototypes.

<Check id="w1-js-5">Promises and async error handling</Check>

`Promise.all` rejects on the first rejection. `allSettled` waits for all and reports each outcome. `race` settles with the first to settle. `any` resolves with the first fulfilment. In `async` functions use `try/catch` around `await`; an unhandled rejection is a bug in production.

<Check id="w1-ts-1">`unknown` versus `any`, narrowing, type guards</Check>

`any` switches the checker off. `unknown` forces you to narrow (`typeof`, `instanceof`, `in`, a user-defined guard `x is T`) before use.

<Check id="w1-ts-2">Generics and constraints</Check>

`function pick<T, K extends keyof T>(obj: T, key: K): T[K]` ties the key to the object. Know when a generic is needed (relating types) versus when a union is enough.

<Check id="w1-ts-3">Utility types and discriminated unions</Check>

`Partial`, `Required`, `Pick`, `Omit`, `Record`, `ReturnType`, `Awaited`. A union with a literal `kind` field lets the compiler narrow exhaustively; add a `never` check to catch missing cases.

<Check id="w1-ts-4">`interface` versus `type`, `satisfies`, `as const`</Check>

Interfaces can merge and are good for object shapes that others extend; type aliases cover unions, tuples and mapped types. `satisfies` validates a value against a type without widening it. `as const` makes literals readonly and narrow.

Coding drills to do today (deck: JS Coding and Polyfills): debounce, throttle, deep clone, `Promise.all`, `bind`, curry, flatten, an event emitter, an LRU cache.

## Day 6: React and Next.js fundamentals

<Check id="w1-r-1">Render phase versus commit phase, reconciliation, keys</Check>

React calls your components to compute a tree (render, must be pure), diffs it against the previous tree, then applies the minimal DOM changes (commit) and runs effects. Elements of the same type at the same position keep their state; changing `key` resets it. Index keys on reorderable lists cause wrong state reuse.

<Check id="w1-r-2">Rules of hooks and why they exist</Check>

Hooks are stored by call order, so they must run in the same order every render: no conditions or loops. Custom hooks share logic, not state.

<Check id="w1-r-3">`useEffect`: dependencies, cleanup, stale closures</Check>

An effect synchronises with something outside React. Every reactive value it reads belongs in the dependency array. Return a cleanup. A stale closure means the effect captured an old value because it was missing from the array. You often do not need an effect at all: derive values during render, handle events in handlers.

<Check id="w1-r-4">State, batching, and when memoisation helps</Check>

State updates are batched and applied on the next render; use the functional form when the next value depends on the previous one. `useMemo`, `useCallback` and `memo` help only when a measured render is expensive or a referentially stable prop matters. Profile first. The React Compiler can automate much of this in newer setups.

<Check id="w1-r-5">Concurrent features and newer APIs</Check>

`useTransition` and `useDeferredValue` keep urgent updates (typing) responsive while slow ones render in the background. `Suspense` declares loading boundaries. React 19 adds Actions (`useActionState`, `useOptimistic`, `useFormStatus`), the `use` API, and ref as a regular prop. Check the current React docs for the version your target company uses.

<Check id="w1-r-6">Server Components versus Client Components</Check>

Server Components render on the server, ship no component JavaScript, and can read data directly, but cannot use state, effects or browser APIs. A `"use client"` file marks the boundary where interactivity starts; props crossing it must be serialisable.

<Check id="w1-n-1">Next.js rendering modes and caching</Check>

Know static rendering, dynamic rendering, streaming, and incremental regeneration, and what makes a route dynamic (cookies, headers, uncached fetches). Caching defaults have changed across Next.js 14, 15 and 16, so read the current caching docs before the interview and state which version you are describing.

<Check id="w1-n-2">Micro-frontend trade-offs (your headline topic)</Check>

Options: build-time composition of packages, runtime composition with Module Federation, iframes, web components, edge or server-side composition. Benefits: independent deploys and team ownership. Costs: duplicated or version-skewed dependencies, inconsistent UX, cross-app state and routing, harder testing, larger total payload. A shared design system and strict contracts are what make it work.

<Check id="w1-n-3">Web performance and security basics</Check>

Core Web Vitals: LCP (loading), INP (interaction latency, replaced FID in 2024), CLS (layout shift). Levers: image sizing and priority, code splitting, caching, fewer third-party scripts. Security: XSS (escape output, CSP), CSRF (SameSite cookies, tokens), CORS, `HttpOnly` and `Secure` cookies, short-lived tokens.

Practice in the **[Interview decks](../decks/)**: React and Frontend, React Versions and Internals, Next.js Deep Dive, JavaScript and TypeScript, JS Coding and Polyfills, Performance and Security.
